TENANT INTEGRATION / 0.4

Tenant 应用接入岗位数据采集引擎方案

面向招聘、人才市场或运营系统的最小接入方案。Tenant 应用只负责提交采集意图、控制作业和消费结果；浏览器登录、页面抓取、解析、租约和重试由 crawler-api 与 desktop-agent 完成。

适用组件：crawler-api + desktop-agent当前来源：智联招聘（zhaopin）数据边界：仅返回解析后的岗位原始事实

1. 接入架构与前提

Tenant 应用持有 Caller Token；创建 Job、读取状态/记录、执行控制。
crawler-api 控制面按 tenant 隔离数据；拆分 query 为 Task，维护状态、事件、租约和记录。
desktop-agent 执行面出站轮询领取 Task；使用本机浏览器 Profile 抓取并批量上传记录。
认证与权限：所有 Tenant 请求使用 Authorization: Bearer <Caller Token>。创建需 collection:write，查询需 collection:read，暂停/恢复/取消及回调 Token 轮换需 collection:control。Agent 使用独立的设备凭证和 Session，不与 Tenant Token 混用。

2. 采集任务生命周期

① 提交POST Job，服务端校验租户、来源和回调，按 query 拆 Task。
›
② 执行Agent claim Task，租约有效期内分页抓取、checkpoint、上传记录并续租。
›
③ 结算Task 完成后聚合作业；所有 Task 结束时产生终态事件。

2.1 创建作业

POST /v1/collection-jobs
Authorization: Bearer <caller-token>
Idempotency-Key: tenant-a:collect:01K5...
{
  "externalRequestId": "recruit-20260923-001",
  "source": "zhaopin",
  "queries": [{"keyword":"Java 后端","region":"上海","pageLimit":10}],
  "collectionMode": "full",
  "metadata": {"campaign":"autumn"}
}

返回 202 Accepted、collectionJobId 和 status=queued。同一业务请求的重试必须复用 Idempotency-Key 与 externalRequestId；参数改变会得到 409，不能借此创建第二个作业。

2.2 状态与控制

状态含义 / Tenant 行为允许的下一步
queued作业已接受，Task 等待 Agent。可暂停或取消。
running至少一个 Task 正在执行；可能短暂进入 awaiting_human 等待浏览器登录或验证。可暂停、恢复（仅暂停态）、取消。
pausing / cancelling控制意图已写入，等待 Agent 在 checkpoint 处响应；属于最终落地前的过渡态。轮询直到 paused 或 cancelled。
paused已保存页码 checkpoint，不再领取/执行新页。恢复：重新排队并从 checkpoint 继续；也可取消。
succeeded / partially_succeeded / failed / cancelled终态，记录集可读取；部分成功同时查看 failureCodeCounts。只读；不能再次控制。

控制接口：POST /v1/collection-jobs/{jobId}/pause、/resume、/cancel。查询聚合状态：GET /v1/collection-jobs/{jobId}，其中 taskStatusCounts、processedCount、version 是进度和并发观测依据；需要审计或补偿时可用 GET /v1/collection-jobs/{jobId}/events 游标读取事件。控制是幂等的；终态作业控制返回 409。

3. 如何获取采集到的岗位数据集

推荐把 crawler-api 作为“原始岗位事实集”服务：作业进入终态后读取，或在运行中按固定间隔增量读取。接口使用服务端 createdAt + recordId 的 keyset 游标，不能自行解码或拼接游标，也不应使用 OFFSET。

GET /v1/collection-jobs/{jobId}/records?limit=200&cursor=<nextCursor>
Authorization: Bearer <caller-token>

{
  "items": [{
    "recordId": "...", "source": "zhaopin", "sourceJobId": "...",
    "sourceUrl": "https://www.zhaopin.com/jobdetail/...",
    "keyword": "Java 后端", "region": "上海", "page": 2,
    "fields": {"title":"Java 工程师", "companyName":"...", "salaryText":"...", "description":"..."},
    "collectedAt": "2026-09-23T09:10:00+08:00", "payloadHash": "sha256:...",
    "taskId": "...", "createdAt": "2026-09-23T09:10:04+08:00"
  }],
  "nextCursor": "..."
}
拉取策略
  1. 先读 Job，确认 status 与 processedCount。
  2. 以 limit=200 首次请求；持久化 nextCursor，直到返回 null。
  3. 按 recordId 或 sourceUrl + payloadHash 做本地幂等，不用 collectedAt 排序。
字段使用fields 是业务可消费内容；sourceJobId/sourceUrl 用于来源追溯；keyword/region/page 保留查询上下文；payloadHash 用于内容去重和变更检测。引擎不提供跨来源 canonical job。

4. 事件通知（可选）与可靠性

需要低延迟时，在创建 Job 时配置 callback：提交 Tenant 应用的 HTTP/HTTPS 回调 URL（跨不可信网络推荐 HTTPS）、短期 Bearer Token 和可选 expiresAt（默认 7 天）。URL 必须命中该 tenant 的 allowlist；Token 只用于该 Job 的回调，不是 Caller Token。

事件触发时机Tenant 处理
collection.job.acceptedJob 创建并拆分 Task 后。记录 collectionJobId，开始查询。
collection.job.desired_state_changed暂停、恢复、取消请求被受理。以 Job 查询结果为准，不把事件视为已完成。
collection.job.terminal进入 succeeded、partially_succeeded、failed 或 cancelled。触发全量游标拉取，保存终态和失败码。

Webhook 是至少一次投递：Tenant 必须按 eventId 幂等，2xx 才代表已接收；控制面会对网络错误、408/429/5xx 有界重试，401/403 标记凭证阻塞。投递失败可用 GET /{jobId}/webhook-deliveries 诊断，并通过 POST /{jobId}/webhook-deliveries/{outboxId}/replay 受控重放。

5. 最小接入清单

应用侧必须实现
  • Caller Token 安全存储与按 scope 分发。
  • 创建请求的 Idempotency-Key 复用、超时重试和 401/403/409/422 分流。
  • Job 状态轮询或 Callback 接收；终态后完整拉取记录分页。
  • 本地以 eventId、recordId 去重，并保存游标和原始响应。
上线前验证
  • 为目标 tenant 配置 callback URL allowlist（如使用回调）。
  • 确认 desktop-agent 已登录目标来源，Profile 状态为 ready。
  • 用 1 个 query、1 页数据完成提交、暂停、恢复、取消和终态读取演练。
  • 定义岗位记录保留期、失败告警阈值和 webhook 永久失败处理人。
边界提醒：Agent 不接触 tenant 身份、回调配置或业务 metadata；浏览器 Cookie/Profile 只保留在执行节点。Tenant 应用不要依赖页面 HTML、截图或未在 ParsedJobRecord 合同中声明的字段。
接口前缀以部署环境为准；本文对应 crawler-api 当前 v1 合同。建议将 API schema、错误码和状态机作为联调验收基线。
