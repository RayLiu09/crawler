# 课程标准、岗位画像与业务数据资产平台项目立项文档

## 一、项目建设背景与目标

### 1.1 建设背景

产业岗位变化正在加速，企业招聘信息中的技术栈、业务任务、工具平台和能力要求持续更新。职业教育或企业培训如果仍以静态专业目录、经验型课程设计和零散就业反馈为主要依据，容易出现“课程已经完成、岗位要求已经变化”的错配：课程标准与教学内容难以及时迭代，教师缺少可验证的市场证据，学生学到的知识点也难以映射为企业可识别的岗位能力。

本项目拟建设一个连接“专业教学标准—课程资源—市场岗位—能力画像—业务分析”的数据与应用底座，形成以标准为约束、以岗位需求为反馈、以数据资产为支撑的闭环。项目不是单纯建设爬虫系统，也不是单纯建设课程管理系统，而是建设一套可持续更新的业务知识和数据资产体系。

现有 `crawler-api` 与 `desktop-agent` 已可承担市场岗位数据采集的基础职责：

- `crawler-api` 负责租户隔离、采集任务提交、任务状态控制、Agent 调度、原始岗位记录保存和事件通知；
- `desktop-agent` 负责浏览器 Profile、来源网站交互、分页采集、人工登录/验证协同、断点续采和批量上传；
- 岗位记录已具备来源 URL、来源岗位 ID、关键词、地区、页码、标题、公司、薪资、经验、学历、描述、技能标签等结构化字段，并支持幂等去重和游标分页。

因此，项目建设重点应从“采集引擎可用”进一步延伸到“数据可理解、可归一、可分析、可服务”：在采集原始事实之上构建标准课程库、标准化岗位与岗位/技能画像，并向教学、就业、专业建设和经营管理提供统一资产视图。

### 1.2 总体建设目标

围绕三个核心需求，形成“标准定义—市场观测—分析应用”的业务闭环：

1. **基于专业教学标准构建标准课程库。** 将国家/行业/学校专业教学标准、职业能力标准和课程标准转化为可版本化、可追溯的课程知识结构，明确课程目标、知识技能、实践任务、考核要求及其与岗位能力的对应关系。
2. **构建岗位需求与能力画像体系。** 持续抓取市场岗位需求，对不同来源、不同写法的岗位进行归一化，形成标准岗位、岗位任务画像和岗位核心技能画像，并计算其随时间、地区、行业和职级的变化。
3. **构建业务面数据资产视图。** 将课程、岗位、任务、技能、企业、地区、行业、采集批次和分析指标组织为可查询、可授权、可追溯的数据产品，为专业建设、课程优化、就业服务和管理决策提供统一事实来源。

### 1.3 建设原则与边界

- **标准先行、数据反馈。** 教学标准是课程库的主约束，岗位数据用于验证和发现变化，不以单次热门岗位直接替代专业标准。
- **原始事实与业务结论分层。** 采集引擎保存来源事实；归一、画像和指标在业务数据层生成，并保留规则、模型版本和证据链。
- **可追溯、可版本化。** 每个课程、岗位归一结果、技能映射和指标均记录生效时间、来源、处理版本和审核状态。
- **租户隔离、最小授权。** 不同学校、企业或业务租户的数据按授权范围访问；Agent 不接触租户身份和业务元数据。
- **先建设最小可用闭环。** 首期聚焦 1—2 个专业方向、1 个主要岗位来源和有限地区，跑通“标准课程—岗位采集—画像—视图—应用”链路后再扩展。

## 二、业务痛点与需求分析

### 2.1 课程建设痛点

| 痛点 | 具体表现 | 直接影响 |
| --- | --- | --- |
| 标准分散 | 专业教学标准、人才培养方案、课程标准、职业技能等级标准分别存放，缺少统一编码和版本关系 | 课程目标难以复用，修订成本高 |
| 课程与岗位脱节 | 课程通常以教材章节或教师经验组织，缺乏与岗位任务、技能要求的明确映射 | 学习成果难以被企业理解，学生就业适配度不足 |
| 课程更新滞后 | 市场技术栈、工具和业务流程变化无法及时反馈到课程大纲 | 课程内容过时，实训项目与真实工作脱节 |
| 评价不可量化 | 只有课程完成率、考试成绩等教学指标，缺少岗位能力覆盖度和市场匹配度 | 专业调整缺少客观证据 |

### 2.2 岗位数据与画像痛点

| 痛点 | 具体表现 | 直接影响 |
| --- | --- | --- |
| 来源异构 | 不同招聘网站字段、命名、详情结构和分页规则不一致 | 数据采集与清洗重复建设，质量不稳定 |
| 岗位命名混乱 | “Java 后端工程师”“后端开发”“Java 开发工程师”等名称指向相近岗位 | 岗位数量和需求趋势被重复计算或误分组 |
| 任务信息隐含 | 岗位描述包含职责、产出、工具、协作对象，但未拆成可比较的任务单元 | 无法从“岗位名称”进一步回答需要完成什么工作 |
| 技能表达不统一 | 同一技能存在中英文、缩写、版本号和工具品牌多种写法 | 技能热度、课程覆盖度和缺口分析不准确 |
| 采集结果难复用 | 只有原始页面或一次性报表，没有稳定的岗位主数据和证据链 | 后续分析无法复算，跨周期比较困难 |

### 2.3 业务分析与资产管理痛点

- **数据分散在系统和文件中。** 课程、岗位、企业、专业、就业和采集任务各自建表，无法按“专业—课程—岗位—技能—企业”穿透分析。
- **指标口径不一致。** “岗位需求量”“核心技能”“课程覆盖率”“紧缺技能”等指标缺少统一定义，部门之间的报表不能直接比较。
- **业务侧难以自助使用。** 管理者需要人工找数、导表和二次加工，无法按地区、行业、职级、时间窗口快速查看变化。
- **数据治理不足。** 原始记录、清洗结果、人工修订和模型推断混在一起，缺少质量状态、责任人、审核流程和失效机制。

### 2.4 业务需求归纳

项目至少需要满足以下业务要求：

1. **标准课程库要求：** 支持专业、课程、模块、知识点、技能点、实践任务、评价指标等对象；支持树状目录、标签、版本、生效/失效时间、审核状态和引用关系。
2. **岗位数据要求：** 支持采集任务的创建、暂停、恢复、取消、进度查询和失败追踪；支持来源记录幂等、分页交付和增量采集；原始记录不可被业务归一结果覆盖。
3. **岗位归一要求：** 支持岗位名称、职级、行业、任务和技能的标准词典；保存原始值、标准值、匹配方法、置信度、规则/模型版本和人工确认记录。
4. **画像要求：** 生成标准岗位画像、岗位任务画像、岗位核心技能画像，并按时间、地区、行业、企业规模等维度统计需求量、占比、增长率和共现关系。
5. **资产视图要求：** 提供专业负责人、教师、就业人员、企业合作人员和管理者所需的主题视图；视图结果可追溯到岗位记录、课程版本和处理批次。
6. **安全与运营要求：** 租户隔离、分级授权、敏感凭证保护、采集质量监控、失败重试、数据保留策略和审计日志必须纳入一期设计。

## 三、项目提供的解决方案

### 3.1 总体方案架构

项目采用四层架构：

```text
标准与业务定义层
  专业标准、课程标准、职业标准、岗位词典、技能词典、指标口径
          ↓
采集与事实数据层
  crawler-api、desktop-agent、采集任务、原始岗位记录、事件与批次
          ↓
标准化与画像加工层
  岗位归一、企业/行业归一、任务抽取、技能归一、画像计算、质量审核
          ↓
业务数据资产与应用层
  课程建设视图、岗位趋势视图、课程-岗位匹配视图、技能缺口视图、管理驾驶舱
```

其中，采集与事实数据层延续现有引擎能力；新增的标准化、画像和数据资产服务不直接修改原始岗位记录，而是通过版本化加工表或主题数据集引用原始事实。

### 3.2 方案一：专业教学标准与标准课程库

#### 3.2.1 课程库对象模型

建立统一的课程知识模型，建议包含以下核心对象：

| 对象 | 关键内容 | 作用 |
| --- | --- | --- |
| 专业 | 专业代码、名称、层次、适用标准、生效周期 | 课程和岗位分析的组织边界 |
| 课程 | 课程代码、名称、学分/学时、适用专业、版本、状态 | 课程主数据和版本管理 |
| 教学模块 | 模块目标、知识点、技能点、实践项目、先修关系 | 组织教学内容和能力递进 |
| 标准要求 | 标准条款、职业能力、证书/等级要求、来源版本 | 保证课程建设有据可依 |
| 评价指标 | 学习成果、实训产出、考核方式、达成度 | 支撑教学质量和能力评价 |
| 映射关系 | 课程/模块—岗位任务—技能—标准条款 | 建立课程与就业需求的可解释连接 |

#### 3.2.2 建设方式

1. **标准采集与拆解：** 导入专业教学标准、人才培养方案、课程标准和职业技能标准，拆分为专业目标、能力要求、知识点、技能点和评价要求。
2. **统一编码与词汇管理：** 为专业、课程、模块、技能和标准条款分配稳定编码；同义词、缩写、旧名称通过词典和别名关系管理。
3. **版本与审核：** 课程库采用草稿、评审、发布、停用状态；每次修订生成新版本，旧版本保留，不覆盖历史教学和分析结果。
4. **形成课程能力图谱：** 以“课程模块—知识/技能—实践任务—评价指标”为主线，记录先修关系、覆盖关系和能力层级。
5. **与岗位反馈闭环：** 岗位画像发现的新技能进入候选池，经专业负责人审核后进入标准词典或课程修订建议，不直接自动改动已发布课程。

首期建议选择一个岗位变化快、数据量适中且已有教学基础的专业方向，例如软件技术、电子商务或智能制造相关专业，先完成 20—50 门课程的标准化建库。

### 3.3 方案二：岗位采集、归一与画像

#### 3.3.1 采集任务与原始事实

Tenant 应用通过 `crawler-api` 提交采集 Job，每个关键词/地区组合拆为独立 Task，由 `desktop-agent` 领取执行。系统支持：

- 任务状态查询、暂停、恢复、取消和终态事件；
- Agent 租约、心跳、checkpoint、断点续采和批量记录上传；
- `sourceUrl + payloadHash` 去重、批次幂等和 `createdAt + recordId` 游标分页；
- 按租户的 Caller Token、数据访问 scope 和回调 URL 白名单；
- 原始字段与采集时间保留，便于复查来源、重算归一规则和解释分析结论。

采集引擎负责回答“来源页面上看到了什么”，不负责直接决定“这个岗位属于哪个标准岗位”。后者由标准化加工层完成。

#### 3.3.2 岗位标准化流程

```text
原始岗位记录
  → 字段清洗与语言规范化
  → 岗位名称/职级/行业/地区/企业归一
  → 职责句切分与任务分类
  → 技能实体识别、同义词合并、版本归一
  → 规则/模型匹配与置信度计算
  → 人工抽样审核与词典回写
  → 标准岗位与画像数据集
```

归一结果建议至少保存：`raw_value`、`normalized_value`、`standard_id`、`match_method`、`confidence`、`processor_version`、`review_status`、`evidence_record_ids` 和 `valid_from/valid_to`。这样既可以批量处理，也允许对低置信度结果进行人工修订和回溯。

#### 3.3.3 三类画像

- **标准岗位画像：** 岗位名称、岗位族、职级、行业、地区、企业规模、需求量、薪资区间、经验/学历分布、需求趋势和代表性企业。
- **岗位任务画像：** 典型工作任务、任务频次、任务前置知识、工具/平台、交付物、协作对象和任务复杂度。任务来源于岗位职责与要求文本，保留原文证据。
- **岗位核心技能画像：** 技能名称、技能类别、共现岗位、需求频次、增长率、职级分布、关联课程和覆盖缺口。核心技能不只按出现次数确定，还应结合岗位覆盖率、任务关键性、时间趋势和人工审核。

首期建议先覆盖标题、职责、要求、薪资、经验、学历、地区、行业和技能标签等高价值字段；对自由文本的任务抽取和技能识别采用“规则词典 + 模型候选 + 人工抽样”的混合方式，避免完全依赖黑盒模型。

### 3.4 方案三：业务面数据资产视图

#### 3.4.1 主题资产域

围绕业务使用场景建设五类主题资产：

1. **课程标准资产：** 专业、课程、教学模块、标准条款、知识技能点、实践任务、评价指标和版本关系。
2. **岗位市场资产：** 标准岗位、岗位族、岗位需求、企业、行业、地区、职级和时间序列。
3. **任务技能资产：** 标准任务、工具平台、技能实体、技能层级、技能共现和技能趋势。
4. **课程岗位匹配资产：** 课程/模块覆盖的岗位任务和技能、覆盖度、缺口、建议补充内容、证据岗位集合。
5. **数据治理资产：** 采集批次、来源、处理版本、质量评分、审核记录、指标口径和数据血缘。

#### 3.4.2 业务视图

| 使用角色 | 关键视图 | 典型问题 |
| --- | --- | --- |
| 专业负责人 | 专业岗位需求与课程覆盖视图 | 本专业对应哪些标准岗位？课程覆盖了哪些高频技能？ |
| 教师/课程负责人 | 课程更新建议视图 | 哪些岗位任务变化最快？课程模块需要增加哪些工具和实训任务？ |
| 就业与校企合作人员 | 企业与岗位趋势视图 | 哪些地区/行业/企业正在扩大招聘？岗位薪资和技能要求如何变化？ |
| 教学管理者 | 专业建设驾驶舱 | 各专业的岗位匹配度、技能缺口和课程更新进度如何？ |
| 数据/运营人员 | 采集与资产质量视图 | 采集是否完整？低置信度归一结果和失效词典有哪些？ |

#### 3.4.3 指标口径

一期建议冻结以下基础指标，避免各部门自行解释：

- **岗位需求量：** 在指定时间窗内，经去重后的标准岗位记录数；可按来源、地区、行业和企业去重策略分别统计。
- **技能需求率：** 包含某标准技能的标准岗位数 / 纳入统计的标准岗位总数。
- **课程技能覆盖率：** 课程已覆盖的目标技能权重 / 目标岗位核心技能权重。
- **岗位任务覆盖率：** 课程实践任务可对应的岗位任务权重 / 目标岗位任务总权重。
- **技能缺口：** 达到核心阈值且课程覆盖不足的技能集合，并附岗位证据、时间趋势和置信度。
- **数据质量得分：** 完整性、唯一性、及时性、归一置信度和人工审核通过率的加权结果。

所有指标应支持按日/周/月刷新，并携带统计周期、样本范围、规则版本和更新时间；不建议将模型推断结果与原始采集记录混成一张不可解释的宽表。

### 3.5 实施阶段与验收建议

| 阶段 | 主要工作 | 阶段产出 |
| --- | --- | --- |
| 第一阶段：标准与样板 | 选择试点专业，整理标准、课程和岗位词典；接入一个岗位来源 | 课程标准库 v1、岗位采集样板、指标口径 |
| 第二阶段：岗位归一与画像 | 建立岗位/技能/任务归一规则，完成抽样审核和画像计算 | 标准岗位库、任务画像、核心技能画像、质量报告 |
| 第三阶段：资产视图 | 建设主题数据集、权限、查询接口和管理视图 | 专业视图、课程视图、岗位趋势视图、技能缺口视图 |
| 第四阶段：闭环运营 | 以岗位变化驱动课程评审，持续维护词典、规则和版本 | 课程更新闭环、月度/季度分析机制、运营手册 |

建议将以下内容作为一期验收基线：

- 试点专业课程标准对象可查询、可版本化、可追溯；
- 采集任务可提交、控制、完成，并能分页获取原始岗位数据集；
- 标准岗位、任务和技能归一结果具有来源证据、版本和审核状态；
- 至少形成专业负责人、课程负责人和管理者三类业务视图；
- 对同一批岗位可以复算画像与指标，规则升级不会破坏历史版本；
- 租户越权访问、重复采集、重复记录、Webhook 重试和低质量数据均有明确处理机制。

### 3.6 项目预期价值

项目完成后，将形成一条可持续运行的业务链路：专业标准定义课程边界，市场岗位反映真实需求，岗位任务和技能画像解释企业需要，业务资产视图支持专业与课程决策，课程调整结果再通过下一周期岗位数据验证。其核心价值不在于新增一组报表，而在于建立可追溯、可更新、可复用的“教学供给—产业需求—数据决策”共同底座。
