01. 目标与边界

本项目产出一个独立岗位需求数据采集引擎。调用方提交来源、关键词、地区和页数等通用采集条件；引擎异步完成任务调度、桌面 Agent 执行、记录接收和结果交付。

引擎范围内

  • 采集作业创建、查询、暂停、恢复和取消
  • Agent 独立身份认证、能力发现、租约和故障恢复
  • 招聘来源适配、页面解析和人工验证协作
  • 解析后原始岗位记录的幂等存储与分页交付
  • 状态事件、操作审计和可靠 webhook 通知

明确不在范围内

  • 任何现有或未来上游系统的适配代码
  • 项目、专业、培养方案和关键词生成规则
  • 岗位主数据合并、跨来源标准化和业务分析
  • 原始 HTML、截图、Cookie 和浏览器 Profile 存储
  • 验证码自动绕过及招聘网站账号托管
数据边界解释 “只存储解析后的原始岗位数据”约束岗位内容，不表示可以删除任务运行元数据。异步任务要支持重启恢复、暂停和取消，仍必须保存作业、子任务、租约、Agent、事件和 Outbox 状态。

03. 组件职责

Auth Gateway

依据配置白名单验证 tenantKey，签发随机访问 Token，并按数据库中的 Token 状态完成每次请求鉴权。

Public API

使用 Bearer Token 识别租户、幂等创建作业、执行状态控制、提供游标分页结果和事件查询。

Agent API

验证受控安装过程预置的设备身份并签发 Agent 会话，在全局任务池中完成能力匹配、原子领取、续租、检查点和解析记录接收；不接受 tenantKey 或 tenantId。

Collection Domain

维护 desired state 与 actual state、合法状态转换、任务汇总和恢复策略。

Lease Coordinator

使用 PostgreSQL 行锁分配任务，通过 lease token 与 fencing token 拒绝迟到写入。

Desktop Agent

以主进程维持心跳，以受监督子进程运行 Selenium；断网时暂存待确认记录。

Source Adapter

封装来源 URL、选择器、登录检测和字段提取，不导入 API 仓储或上游模型。

Parsed Record Store

追加保存从列表页和详情页解析出的来源事实；只做确定性去重，不构建岗位主数据。

Webhook Outbox

与状态变更同事务写入事件，异步使用该 Job 的短期 Callback Token 访问上游回调 API；调用方按 event ID 去重。Token 一次签发、限定单 Job/单接口，在有效期内允许幂等重试。

04. 数据采集处理流程

调用方先完成 tenantKey 换取访问 Token，再提交异步作业。HTTP 请求只创建持久化作业，不等待 Selenium；任务事实、租约和记录确认都以 PostgreSQL 为准。01 至 11 是正常完成路径，12 至 14 是执行期间按条件进入的分支，不是依次必经步骤。

申请访问 Token调用方提交 tenantKey；Auth Gateway 校验配置白名单，持久化 Token 哈希并将明文 Token 返回一次。
提交采集作业调用方使用 Caller Token，并在请求体随 callback URL 提交单 Job 短期 Callback Token 和 expiresAt；控制面保存 Token ciphertext 与本地 fingerprint，返回 202 与 collectionJobId。
拆分采集任务API 按查询条件创建 collection_tasks，冻结请求快照，不再依赖调用方在线。
Agent 能力与 Profile 同步已认证 Agent 心跳上报版本化 capabilities、动态空闲槽和本机 Profile 元数据；API 先完成校验与 upsert，再在全局任务池使用 SKIP LOCKED 原子领取，不向 Agent 暴露租户信息。
建立执行租约API 返回 leaseToken、fencingToken 和过期时间；Agent 独立心跳线程持续续租。
桌面浏览器采集来源 Adapter 打开列表及详情页，在页级和记录级安全点读取控制信号。
解析与本地暂存DOM 被解析为 ParsedJobRecord；Agent spool 保存未被 API 确认的批次，不保存 HTML。
幂等批量写入API 校验租约和哈希，使用唯一键忽略重复记录，并确认 acceptedRecordIds。
循环采集与检查点每页记录确认后更新 pageCheckpoint；未达到 pageLimit 时继续导航，避免恢复后遗漏或重复推进。
完成与汇总Agent 提交任务终态；API 汇总所有子任务并生成 succeeded、partial 或 failed。
结果交付Dispatcher 解密该 Job 的有效 Callback Token，通过 Authorization: Bearer 投递事件；上游按 event ID 幂等处理，岗位明细仍通过稳定游标分页获取。
条件分支 12-14从执行阶段按控制信号、页面状态或租约状态进入；处理后返回主干、保持暂停或终止。
控制分支暂停处理Agent 停止新导航、清空 spool、保存 pageCheckpoint、关闭浏览器并释放租约。
人工介入分支人工验证检测到登录或验证页时进入 awaiting_human；执行机操作同一浏览器后自动继续。
异常恢复分支故障恢复租约到期后依据 desiredState 决定重排队、保持暂停或取消，旧 fencingToken 失效。

05. 任务状态与控制

作业和子任务均保存 desired_state 与 status。前者表达控制意图，后者表达执行事实。

queued→running→succeeded / partially_succeeded / failed
running→pausing→paused→queued
running→awaiting_human→running或cancelling→cancelled
场景中心端处理Agent 处理最终状态
暂停queued 任务立即变为 paused；活动任务设置 desired_state=paused 并进入 pausing，不清除租约完成安全检查点、确认上传、关闭浏览器、释放租约所有未终态任务确认后为 paused
恢复仅 status=paused 时接受；paused 任务恢复 queued，保留检查点；重复 resume 为无版本变化的幂等返回重新领取并从 page_checkpoint 继续queued，领取后 running
取消queued/paused 立即 cancelled；活动任务进入 cancelling，不提前作废运行任务写权限或清租约协作退出；超时后由 Supervisor 终止子进程树所有活动任务确认后为 cancelled
Agent 失联租约到期并递增 fencing_token重连后旧租约写入得到 409依 desired_state 决定

08. API 与 Agent 协议

调用方认证

控制中心是纯 API 服务，不建设租户管理 GUI。通过只读 Secret 文件维护 tenantKey 白名单，白名单是调用方授信的唯一配置源；api_clients 和 api_access_tokens 不反向成为新增租户的授权来源。tenantKey 应为高熵随机值，服务端使用常量时间比较验证其哈希。

version: 1
tenants:
  - tenantId: tenant-a
    displayName: 上层应用 A
    enabled: true
    tenantKeyHashes:
      - "sha256:<key-fingerprint>"
    # scopes 可选；省略时为 collection:write、collection:read、collection:control
    callbackAllowlist:
      - "http://upstream.internal/api/job-collection/events"

初始 API 权限全集为 collection:write（创建作业）、collection:read（查询作业、事件和岗位记录）、collection:control（暂停、恢复、取消和 Callback Token 轮换）。callbackAllowlist 按 tenant 配置允许的规范化 HTTP 或 HTTPS 完整 URL；创建 Job 时必须精确匹配，禁止 userinfo、fragment 和重定向跟随，避免通过 URL 变体或 3xx 绕过目的地址限制。HTTP 用于受信任内网，跨不受信任网络时由部署方配置 HTTPS。配置文件不进入镜像，由部署系统以只读 Secret 挂载。服务启动时必须完成 schema、重复 tenantId、重复 Key 指纹、scope 和 callback URL 校验，配置无效时启动失败。白名单修改通过代码评审或受控运维流程发布；不提供创建、删除或修改租户的公共 API。

配置与数据库一致性白名单是最终授信依据。服务启动或受控重载时，在事务中将白名单启用项同步到 api_clients；配置中已禁用或移除的 tenant 必须被标记为 disabled，并吊销其所有未过期 api_access_tokens。数据库中残留的 active 行不能让已移除 tenant 继续访问。tenantKey 轮换通过同一 tenantId 临时配置新旧两个哈希完成，迁移结束后再删除旧哈希。

1Auth Gateway读取只读白名单配置，按 tenantKey 哈希匹配启用条目；不匹配统一返回 401，并进行申请频率限制。
2api_clients仅在白名单匹配成功后，按配置 tenantId 查询启动时已同步的 client；要求记录存在、状态 active 且 config_fingerprint 与当前白名单一致，否则统一返回 401。签发请求不创建或修复 client。
3Credential Service使用安全随机源生成带 cat_ 前缀的 32 字节高熵、不透明 Bearer Token，并使用独立 API_TOKEN_HASH_KEY 计算 HMAC-SHA256 token_hash。
4api_access_tokens在同一事务内把 client 当前 allowed_scopes 复制为 scopes，并写入 client_id、token_hash、issued_via_key_fingerprint、issued_at 和 expires_at；明文 Token 不落库。
5调用方明文 Token 仅在成功响应中返回一次，调用方负责安全保存并在后续请求中使用。
6Bearer 鉴权中间件对请求 Token 计算哈希，联查 Token 未过期/未吊销且 client active，再把 client_id 注入请求上下文。

受控重放资格接口要求 collection:control 和非空、最长 200 字符的 Idempotency-Key。只有状态为 permanently_failed 且 lastFailureCode 为 retry_exhausted_* 的记录可重放；协议型 3xx/4xx 永久失败不能借此自动重试。Outbox 不得存在 claim，Callback ciphertext/nonce 必须仍可用且 Token 尚未过期。凭证已销毁、过期、状态不符或使用新操作键重放已经恢复的记录均返回 409；未知 outbox、跨 Job 或跨 tenant 均返回相同 404。
重试预算、幂等与锁序受理事务先通过 Event/Job/client 联查锁定 Outbox，再锁定 callback 配置，与 Dispatcher 的 Outbox → callback 锁序一致。事务把状态改为 pending、attemptCount 归零、replayCount 加一、nextAttemptAt 设为受理时间并清除旧失败码；因此新轮次重新获得完整自动重试预算。此前尝试次数和失败码写入永久 replay 历史。数据库只保存 Idempotency-Key SHA-256；同一键即使在后续 delivered 或更多重放后再次提交，仍返回首次结果，不重复修改 Outbox。

Outbox 事件目录（schemaVersion 1）

webhook_outbox 不定义另一套事件类型，它只负责可靠投递同一事务写入的 collection_events。0.4 冻结以下三种事件；只有创建 Job 时配置了 Callback，事件才会产生对应 Outbox 记录。

eventType触发时机与出现次数payload（camelCase）回调应用建议处理
collection.job.accepted 新 Job、子任务与 Callback 配置完成同事务持久化时产生；每个 Job 恰好一次。创建接口的幂等重放不重复产生。 source；desiredState="running"；status="queued"；taskCount 建立或确认上游侧 Job 映射，记录已被控制面受理；不能据此判定 Agent 已开始执行。
collection.job.desired_state_changed pause、resume 或 cancel 确实改变 Job 控制意图时产生；每个 Job 可出现多次。相同控制命令的幂等重放不重复产生。 action：pause | resume | cancel；变更后的 desiredState 与 status 更新控制意图和当前聚合状态。pausing、cancelling 只表示协作控制已持久化，不能当作操作已完成。
collection.job.terminal Job 首次聚合为终态时产生；每个 Job 恰好一次。终态包括 cancelled、succeeded、partially_succeeded、failed。 status；processedCount；failureCodeCounts；completedAt 完成上游流程并按需通过 Records API 拉取岗位明细。该事件只提供汇总，不携带岗位记录。
事件感知边界0.4 不为 queued → running、running → awaiting_human、暂停完成、Agent 上下线、Profile 登录状态、单个 Task 状态和单批岗位记录生成 Webhook 事件。需要这些中间态时，上游通过 Job 查询接口读取当前聚合快照；不要把“长时间未收到新事件”解释为失败。后续增加事件类型必须提升事件契约版本或保持 schemaVersion 1 的向后兼容，回调应用应忽略未知 eventType，而不是使整个回调端点失败。
信封、顺序与去重所有类型共享 eventId、eventType、occurredAt、collectionJobId、externalRequestId、jobVersion 和 payload。事件信封不包含 tenantId、clientId、Agent、Profile、租约、Caller Token 或 Callback Token。投递为至少一次，上游必须以 eventId 持久化去重，重复事件仍返回任意 2xx 且不得重复执行业务副作用。jobVersion 用于识别迟到事件，但同一事务产生的控制事件与终态事件可能共享 jobVersion；同版本时按业务语义处理，不能依赖 UUID 或到达顺序推断先后。
投递结果分类任意 2xx 表示已接受且 Outbox 标记 delivered；响应正文不参与协议。连接失败、超时、408、425、429 和 5xx 进入有界指数退避，429/503 可读取受上限约束的 Retry-After。401/403 将 Outbox 标记为 credential_blocked，等待调用方轮换 Token，不做无意义高频重试。其他 4xx 记为永久失败。控制面禁止自动跟随 3xx 重定向，防止 callback allowlist 被绕过。
Dispatcher 并发与恢复API 生命周期默认启动 4 个可配置 worker。worker 使用 FOR UPDATE SKIP LOCKED 领取 status=pending、已到 nextAttemptAt 且无有效 claim 的一条记录，在数据库提交 30 秒短租约后才执行网络调用，因此不会在 Job 状态事务或数据库行锁内等待 HTTP。结算使用 outboxId + claimId 比较并交换；租约到期可由同实例其他 worker 或另一 API 实例接管，旧 worker 的迟到结果不能覆盖新持有者。该机制仍是至少一次而非恰好一次，上游必须按 eventId 去重。
重试与凭证竞争默认 HTTP 超时 10 秒、最多 8 次实际请求、基础退避 5 秒、退避上限 900 秒；429/503 的 Retry-After 支持秒数和 HTTP-date，并受独立上限约束。达到最大次数后标记 permanently_failed。Callback Token 在本地已过期或无法解密时直接 credential_blocked，不发 HTTP 且不增加 attemptCount。旧 Token 的 401/403 与轮换并发时，结算再次比较 credentialVersion；版本已经变化则保持 pending 并立即改用新凭证，不能由旧响应重新封锁。
HTTP 最小暴露Dispatcher 发送冻结 JSON 信封、Bearer Token 和 eventId 幂等键，禁止自动跟随重定向并关闭环境代理读取。实现不读取回调响应正文；网络错误只保存 timeout 或 connection_error 等稳定失败码，不把 Callback URL、Authorization、Token、响应正文或底层异常文本写入 Outbox 和应用日志。专用 Transport 将 httpx/httpcore 依赖日志固定为 WARNING，避免其默认 INFO/DEBUG 请求日志绕过应用审计边界并输出完整 Callback URL。
端到端故障验收真实 PostgreSQL Outbox、AES-GCM 凭证解密、Dispatcher、httpx Transport 与回环 TCP Callback 服务已组成完整自动化链路。测试注入 503/Retry-After、服务端断连、读超时、307、401 后凭证轮换，以及 claim 到期后的并发接管；验证指数退避、禁止重定向、相同 eventId 至少一次投递、新旧 Token 切换、迟到结算 fencing 和 URL/Token/响应正文脱敏。该验收不包含已明确延期的 DNS/IP 分类、连接地址固定与 DNS rebinding 防护。
指标、告警与安全审计GET /internal/metrics 提供 Prometheus 格式的 Webhook 聚合指标且不进入 OpenAPI。数据库实时 Gauge 包含 pending、最老 pending 年龄、credential_blocked、permanently_failed、retry_exhausted 和活动 claim；进程 Counter/Histogram 包含各结算结果、投递耗时、过期 claim 接管、陈旧结算、重试耗尽和 Dispatcher 异常。指标标签只使用固定 result 集合，不使用 URL、tenant、Job、Event、Outbox 或失败文本。每次结算输出单行 JSON 审计，字段限定为 Event/Job/Outbox ID、credentialVersion、attempt、结果和受控失败码。指标端点不使用 tenant Caller Token，生产由反向代理或网络策略仅允许监控网络访问；多 API 副本需逐实例抓取进程 Counter。
至少一次语义与最终销毁Callback Token 不能在第一次 HTTP 请求后立即消费失效。上游可能已经提交事件事务但响应在网络中丢失，控制面必须能用相同 Token 和 eventId 重试。Token 的“一次性”只表示每个 Job 单独签发、权限单一并有七天上限。每次 delivered 结算都会串行锁定 callback 配置；只有 Job 已终态且该配置不存在任何其他非 delivered Outbox 时，才在同一事务把 ciphertext/nonce 置空并记录 credentialDestroyedAt。credential_blocked、permanently_failed、非终态 Job 或尚有并发投递均不触发提前销毁；销毁完成后上游可立即吊销对应 Token。

Agent API

Agent 使用独立的设备身份和 agent_sessions，不提交 tenantKey，也不访问调用方 Token 接口。首次信任建立分为“安装前预置”和“运行时建会话”两个阶段。collection_agents 由控制中心侧的非 HTTP provisioning CLI 使用运维权限预先写入，并不依赖 Agent Session；Agent Session 只在预置身份验证成功后创建，因此不存在循环依赖。

阶段 A：受控安装前置预置（此时不需要 Agent Session）
  1. 授权运维流水线在控制中心侧运行 provision-agent CLI
  2. CLI 生成唯一 agentId + 高熵 deviceSecret
  3. CLI 通过数据库事务写入 collection_agents(id, display_name,
     device_credential_hash, status=offline)，capabilities 使用版本化默认值：
     {"schemaVersion":1,"supportedSources":[],"maxConcurrentTasks":1,
      "browser":{"name":"chrome","headful":true}}
  4. 明文 agentId + deviceSecret 仅一次性交付给对应执行机并写入系统凭据存储

阶段 B：Agent 首次启动及后续运行时认证
  5. Agent 调用 POST /v1/agent/sessions，提交 agentId + deviceSecret
  6. API 查询预置的 collection_agents，并以常量时间校验凭证哈希和设备状态
  7. 校验成功后 API 才写入 agent_sessions(session_token_hash, expires_at)
  8. 明文短期 Agent Token 仅返回一次，后续心跳和任务接口使用该 Token
Provisioning CLI 约束控制中心镜像提供非 HTTP 的 provision-agent --display-name "..." 命令；安装编排器重试同一请求时复用显式 --agent-id，已有 ID 会被拒绝且不会重新发放凭证。CLI 只把明文 deviceSecret 作为一次性 JSON 标准输出交付，数据库仅保存使用独立 AGENT_DEVICE_CREDENTIAL_HASH_KEY 计算的 HMAC 哈希。未指定 ID 时由安全随机源生成新的 UUID。
执行机凭据与托管托管配置只保存 keyring service/username，Agent 启动时从当前专用账号的系统凭据库读取 deviceSecret；Windows 对应 Credential Manager，Linux 对应图形会话中已解锁的 Secret Service。凭据命令使用隐藏输入和二次确认，不接受 secret 命令参数且不输出 secret。由于可见浏览器和人工验证依赖交互桌面，Windows 使用 Interactive 登录计划任务而不是 Session 0 Service；Linux 使用 systemd user service + desktop autostart，而不是系统级 daemon 或 user lingering。
Bootstrap 边界POST /v1/agent/sessions 是设备凭证换取短期会话的认证接口，不是 Agent 注册接口，不允许在找不到 agentId 时自动创建 collection_agents。provision-agent CLI 不对公网暴露，不使用调用方 Token，也不绑定 tenant；其执行审计由部署/运维系统负责。
Session 与凭证生命周期Session 签发、rotate-agent-credential 和 disable-agent 都对目标 Agent 行执行 FOR UPDATE，避免旧 deviceSecret 与轮换并发时产生漏吊销 Session。未知、disabled 或凭证错误统一返回 401；未知 ID 仍执行一次虚拟 HMAC 比较。Session Token 使用独立 AGENT_TOKEN_HASH_KEY 计算 HMAC-SHA256，明文仅返回一次。轮换和禁用在修改 Agent 的同一事务中吊销全部未过期 Session，轮换不会隐式启用 disabled Agent。

Agent Session 只证明执行机身份，不包含 tenant。控制中心从全局排队任务中按来源能力、Profile 可用性、优先级和公平策略选择任务；Agent 不参与租户选择。

活跃租约鉴权与续租每次 heartbeat、checkpoint、complete、release 和记录上传都先验证 Agent Session，再按 Agent → Job → Task 顺序加锁，并同时核验 path/body taskId、Agent/Task/Profile 绑定、当前 attempt、leaseToken HMAC、fencingToken、客户端提交的 leaseExpiresAt 与数据库当前值，以及服务端租约尚未过期。Session 无效统一返回 401；任何租约字段过时、错配或租约已失效统一返回 409。续租响应中的 leaseExpiresAt 是下一次请求必须提交的新值，成功续租后旧值立即失效。
检查点与协作退出checkpoint 只接受不小于数据库当前值的 pageCheckpoint 和 processedCount，且 pageCheckpoint 不得超过 pageLimit；响应同时返回 running、paused 或 cancelled 控制意图。complete 将 completed/failed 写为 succeeded/failed，paused/cancelled 仅在 Job 与 Task 的 desiredState 一致时接受。release 在 running 意图下重排队，在 paused/cancelled 意图下进入对应稳定状态。终止事务同时清除 Task 租约、Agent currentTaskId、完成 attempt 并聚合作业；Profile 仅在当前仍为 busy 时改回 ready，不覆盖 Agent 已上报的 login_required 或 unavailable。
过期回收回收器每个事务只处理一个过期候选：先无锁发现候选，再按 Agent → Job → Task 加锁并重新核验租约未发生变化。running 任务回到 queued，paused/cancelled 意图进入对应状态，attempt 记录 lease_expired；清除绑定时额外递增 fencingToken，使旧执行者即使持有原 leaseToken 也无法迟到写入。当前版本在每次 claim 前执行一次回收，后续可增加独立调度器以降低无领取流量时的回收延迟。

Agent 协议规则Agent 身份认证与调用方 tenantKey 认证相互独立。任务领取响应只包含 attemptId、taskId、source、profileKey、keyword、region、pageLimit、checkpoint 和租约信息，禁止包含 tenantId、clientId、externalRequestId、callback 或调用方 metadata。所有 Agent 写请求同时校验 agentId、taskId、leaseToken、fencingToken 和 leaseExpiresAt；控制中心再经 task → job → client 确定结果的租户归属。
Fake Adapter 验收边界确定性 FakeSourceAdapter 只在内部测试中模拟 zhaopin 协议事实，不增加 fake 公共来源，也不启动浏览器或访问网络。固定查询、页码、页内位置和注入时钟产生相同记录及 payloadHash；页开始和下一条记录开始前检查控制意图，已开始生成的当前记录仍会交付，整页完成后产生累计检查点。自动化测试通过真实 FastAPI 路由和 PostgreSQL 贯通 tenantKey 换 Token、Job 提交、Agent Session/心跳/claim、批次幂等上传、checkpoint、complete、终态聚合和结果 keyset pagination，并验证 Agent 响应不泄露调用方上下文及事务回滚零残留。测试中的 Agent Actor 不是生产桌面运行时，不代表 Transport、SQLite Spool、Supervisor、Profile 锁或真实双节点已经完成。
Zhaopin Adapter 实现边界ZhaopinSourceAdapter 已从旧单体采集器迁移搜索 URL、列表/详情选择器、列表字段优先级、招聘人数提取和 sourceJobId 规则，并直接生成共享 ParsedJobRecord；不再依赖旧 PlatformClient、任务字典、上游状态或业务派生字段。浏览器由构造注入的工厂创建，默认使用本机持久化 Chrome/Edge Profile，并在成功、异常或控制退出时关闭。岗位链接导航前统一为 HTTPS，且必须严格属于 zhaopin.com，拒绝 userinfo、外部域、fragment 和非标准端口。默认城市表只保留已有代码可证实的北京/北京市 530，其他编码必须经验证后显式注入。Adapter 检测 passport.zhaopin.com、路径段 /login、登录提示，以及 Security Verification、TEOCaptchaWidget、正在验证连接安全性；无头模式稳定失败，可见模式保持同一个 driver/Profile 等待人工完成，并仅报告 login_required、verification_required、resumed。等待有界且每次轮询检查暂停/取消，不启动第二个浏览器，不上传 Cookie、Profile、页面源码、截图或验证码内容。控制只在页开始和下一条详情开始前检查；已开始读取的详情会完成当前记录，不因中途命令丢弃。8.3 已通过离线 DOM 契约测试；真实线上页面、人工接管、Profile 重启和双执行机验收仍属于 8.4。

11. 部署与安全

  • 生产控制中心服务器运行独立的 crawler-api 和 postgres 容器；API 镜像基于 Python 3.12 slim，以非 root 用户运行，不包含 Chromium 或 Agent。
  • 生产两个容器加入专用 Docker bridge network。PostgreSQL 不使用 ports 发布 5432，API 通过服务名 postgres 连接；该同主机内部链路按既定方案不启用 TLS。
  • 生产 PostgreSQL 使用 18 系列镜像及独立持久卷或绑定数据盘，并制定备份、恢复、容量、监控和升级策略；数据库账号只授予目标 database/schema 所需权限。
  • API 单实例数据库连接池基准容量为 pool_size=10、max_overflow=0，连接按需建立；API、数据库 Session 和生产 PostgreSQL 时区统一为 Asia/Shanghai。
  • 开发环境不重复部署 PostgreSQL，使用 POSTGRES_* 配置连接 10.100.11.182:5432/crawler；开发密码通过本地 Secret 或未提交的环境文件注入。
  • POSTGRES_SSLMODE 按环境配置：生产同机 Docker 内部链路使用 disable；开发外部数据库的 SSL 模式在连通性验证后确定。
  • Alembic 迁移作为部署前置步骤执行，应用启动不自动修改生产 schema。
  • tenantKey 白名单以只读 Secret 文件挂载到 API 容器，不打入镜像；控制中心不提供租户管理 GUI 或租户增删改公共 API。
  • 白名单变更通过受控部署发布并触发事务性同步；被移除或禁用 tenant 的 api_client 和全部未过期 Token 必须同步失效。
  • 调用方用白名单 tenantKey 申请短期不透明 Token；Token 哈希和生命周期写入 PostgreSQL。Agent 使用另一套设备密钥换取 Agent Token。
  • Agent 唯一设备身份由控制中心侧 provisioning CLI 在安装前预置；CLI 直接使用运维权限写入 collection_agents，不依赖 Agent Session，不增加人工审批或 tenant 绑定。
  • 每台执行机使用不同 deviceSecret，禁止在安装包中嵌入所有机器共用的长期注册密钥；设备长期凭证哈希与短期 Session Token 哈希使用不同密钥域，明文凭证只允许一次性交付并存入操作系统凭据存储。
  • Agent 是全局执行资源，不配置或保存 tenantId；只能领取一个能力匹配的任务，并只能用该任务的有效租约提交检查点和记录。
  • 桌面 Agent 至少部署两个独立节点，并可继续横向扩展；每个节点拥有不同的 agentId、deviceSecret、本地 Spool 和 Browser Profile，任一节点离线后由租约恢复机制把任务重新放回全局任务池。
  • Agent 只发起出站 HTTPS；Profile、Cookie 和账号信息不进入中心日志、API 请求或 PostgreSQL。
  • callback URL 支持 HTTP 和 HTTPS，必须精确命中 client 范围内的完整 URL allowlist，且控制面不自动跟随 3xx。HTTP 仅用于受信任内网，跨不受信任网络时配置 HTTPS。DNS/IP 地址固定与 rebinding 防护因当前采用受控 tenant 白名单而延期，作为明确的遗留安全项，不视为已经解决。
  • 每个启用回调的 Job 使用独立、默认七天、只允许访问指定 callback API 的 Bearer Token。Token 由上游签发并在创建 Job 的 JSON body 中提交，禁止放入 URL/query。
  • 控制面使用独立 AES-256-GCM 密钥保存 Callback Token ciphertext，使用独立 HMAC key 生成本地 fingerprint；明文和可用凭证不得进入 request_payload、事件、Outbox、Agent 载荷、响应、异常或日志。
  • Dispatcher 默认 4 个 worker、10 秒 HTTP 超时、30 秒 claim 租约、最多 8 次请求，参数通过 WEBHOOK_* 环境变量配置；claim 租约必须长于请求超时。
  • /internal/metrics 不进入公共 OpenAPI、不接受 tenant Caller Token，并由生产反向代理或网络策略限制为监控网络访问；Prometheus 告警覆盖积压、最老事件、凭证阻塞、永久失败、重试耗尽和频繁 claim 接管。
  • 上游负责 Callback Token 的 hash、scope、Job/接口绑定和吊销。0.4 不要求控制面与上游共享 digest 算法，也不使用 WEBHOOK_SIGNING_KEY 代替 Callback Token。
  • 执行机使用专用交互式桌面账号；每个 Profile 仅允许一个浏览器进程，Agent Supervisor 负责清理进程树。
  • Windows Agent 以专用用户 Interactive 登录计划任务托管，Linux Agent 以 systemd user service + desktop autostart 托管；配置文件权限收紧且只保存 keyring 定位信息。正常停止先进入 Agent 协作取消和浏览器清理，180 秒超时后托管器才允许强制终止。
